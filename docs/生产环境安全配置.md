## 1. 安全链路评估

### 1.1 完整请求链路

```
┌─────────────────────────────────────────────────────────────────┐
│                    生产环境请求链路                              │
└─────────────────────────────────────────────────────────────────┘

  互联网用户                    Gateway                    内网服务
       │                           │                           │
       │  1. HTTPS 请求            │                           │
       │  Authorization: Bearer    │                           │
       │  ────────────────────────>│                           │
       │                           │                           │
       │                           │  2. 验证 JWT 签名           │
       │                           │  jwtService.parseAndValidate()
       │                           │  - 验证签名（防篡改）      │
       │                           │  - 验证过期时间            │
       │                           │  - 提取 userId, roles      │
       │                           │                           │
       │                           │  3. 添加用户上下文头       │
       │                           │  X-User-Id: {userId}      │
       │                           │  X-User-Roles: {roles}    │
       │                           │  ────────────────────────>│
       │                           │                           │ 4. 读取请求头
       │                           │                           │ 创建 UserContext
       │                           │                           │ UserContextHolder.set()
       │                           │                           │
       │                           │                           │ 5. Service 业务逻辑
       │                           │                           │ requireAdmin() → 检查角色
       │                           │                           │
       │  6. 返回响应              │                           │
       │ <─────────────────────────────────────────────────────│
```

### 1.2 安全依赖点

| 环节 | 安全措施 | 被攻破后果 |
|------|----------|------------|
| **JWT 签发** | 使用密钥签名，包含 userId + roles | 密钥泄露可伪造任意身份 |
| **Gateway 验证** | 验证 JWT 签名和过期时间 | 绕过验证可伪造身份 |
| **用户上下文传递** | Gateway 解析后添加请求头 | 中间人可篡改请求头 |
| **Service 层校验** | requireAdmin() 检查角色 | 依赖上游传递的数据 |

### 1.3 当前设计的安全假设

```
┌─────────────────────────────────────────────────────────────────┐
│  当前架构的安全假设（必须满足）                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ✅ 假设 1：Gateway 是唯一公网入口                               │

│                                                                 │
```

## 2. 潜在风险分析

### 2.1 风险总览

| 风险 | 严重性 | 可能性 | 缓解措施 |
|------|--------|--------|----------|
| Gateway 被绕过 | 🔴 高 | 中 | 网络隔离、防火墙 |
| JWT 密钥泄露 | 🔴 高 | 低 | 密钥管理、轮换 |
| 服务间无认证 | 🟡 中 | 中 | mTLS、API Key |
| UserContext 伪造 | 🟡 中 | 低 | 服务层 JWT 验证 |
| 中间人攻击 | 🟡 中 | 低 | HTTPS、内网加密 |

---

### 2.2 风险详解

#### 风险 1：Gateway 被绕过（🔴 高危）

```
┌─────────────────────────────────────────────────────────────────┐
│  攻击场景：黑客直接访问 user-service                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  攻击步骤：                                                     │
│  1. 扫描发现 user-service:8101 暴露在公网                       │
│  2. 直接发送请求：                                              │
│     POST http://target:8101/api/admin/users/1/ban             │
│     Header: X-User-Id: 1                                       │
│     Header: X-User-Roles: ADMIN  ← 伪造！                       │
│  3. user-service 的 UserContextFilter 读取请求头                │
│  4. 创建 UserContext(userId=1, roles=["ADMIN"])                │
│  5. requireAdmin() 检查通过 → 越权成功！🔴                      │
│                                                                 │
│  根本原因：                                                     │
│  • user-service 信任 X-User-Roles 请求头                         │
│  • 没有二次验证 JWT 签名                                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**检测方式：**
```bash
# 测试 user-service 是否暴露在公网
curl -X GET http://<公网 IP>:8101/api/health

# 如果返回 200，说明服务可直接访问（危险！）
```

---

#### 风险 2：JWT 密钥泄露（🔴 高危）

```
┌─────────────────────────────────────────────────────────────────┐
│  攻击场景：黑客获取 JWT 密钥后可伪造任意身份                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  后果：                                                         │
│  • 伪造 ADMIN 角色的 JWT，获取管理员权限                         │
│  • 伪造任意 userId，访问任意用户数据                            │
│  • 签发永久有效的 Token，长期潜伏                                │
│                                                                 │
│  泄露途径：                                                     │
│  • 代码仓库泄露（密钥硬编码）                                   │
│  • 配置文件明文存储                                             │
│  • 环境变量被读取                                               │
│  • 日志中打印密钥                                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**检测方式：**
```bash
# 检查代码中是否有硬编码密钥
grep -r "jwt.*secret" --include="*.java" --include="*.yml" --include="*.properties"

# 检查密钥是否使用环境变量
grep -r "security.jwt.secret" --include="*.yml"
```

---

#### 风险 3：服务间无认证（🟡 中危）

```
┌─────────────────────────────────────────────────────────────────┐
│  攻击场景：黑客攻破 admin-service 后横向移动                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  攻击步骤：                                                     │
│  1. 黑客在 admin-service 中注入恶意代码                         │
│  2. 通过 Feign Client 调用 user-service：                       │
│     UserServiceClient.banUser(userId)                          │
│  3. FeignRequestInterceptor 添加请求头：                        │
│     X-User-Roles: ADMIN  ← 从当前上下文获取                     │
│  4. user-service 信任请求头 → 执行操作 🔴                       │
│                                                                 │
│  根本原因：                                                     │
│  • 服务间调用仅靠请求头传递身份                                 │
│  • 没有服务级认证（只认证用户）                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 方案 A：服务间 JWT 认证（推荐）

#### 原理

```
┌─────────────────────────────────────────────────────────────────┐
│  服务间 JWT 认证流程                                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  admin-service                      user-service                │
│       │                                   │                     │
│       │  1. Feign 调用前                  │                     │
│       │  签发服务 JWT                     │                     │
│       │  {                                │                     │
│       │    "sub": "admin-service",       │                     │
│       │    "roles": ["SERVICE"],         │                     │
│       │    "exp": now+5min               │                     │
│       │  }                                │                     │
│       │ ────────────────────────────────> │                     │
│       │     Authorization: Bearer <svc-jwt>                    │
│       │                                   │                     │
│       │                                   │  2. 验证服务 JWT    │
│       │                                   │  - 验证签名         │
│       │                                   │  - 验证服务名       │
│       │                                   │  - 验证不过期       │
│       │                                   │                     │
│       │                                   │  3. 验证用户 JWT    │
│       │                                   │  (如果请求有用户)   │
│       │                                   │                     │
│       │                                   │  4. 执行操作        │
│       │ <──────────────────────────────── │                     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 实现代码

```java
// 1. 服务 JWT 签发器
@Component
public class ServiceJwtIssuer {
    private final JwtService serviceJwtService;

    public ServiceJwtIssuer(@Value("${service.jwt.secret}") String secret) {
        this.serviceJwtService = new JwtService(secret, Duration.ofMinutes(5));
    }

    /**
     * 签发服务间调用的 JWT
     */
    public String issueServiceToken(String serviceName) {
        Set<String> roles = Set.of("SERVICE", serviceName.toUpperCase());
        return serviceJwtService.issue(0L, roles); // userId=0 表示服务调用
    }
}

// 2. Feign 请求拦截器 - 添加服务 JWT
@Component
public class ServiceJwtRequestInterceptor implements RequestInterceptor {
    private final ServiceJwtIssuer jwtIssuer;

    public ServiceJwtRequestInterceptor(ServiceJwtIssuer jwtIssuer) {
        this.jwtIssuer = jwtIssuer;
    }

    @Override
    public void apply(RequestTemplate template) {
        String serviceToken = jwtIssuer.issueServiceToken("admin-service");
        template.header("X-Service-Token", serviceToken);
    }
}

// 3. user-service 验证服务 JWT 的过滤器
@Component
public class ServiceJwtValidationFilter extends OncePerRequestFilter {
    private final JwtService serviceJwtService;
    private final List<String> trustedServices;

    public ServiceJwtValidationFilter(
            @Value("${service.jwt.secret}") String secret,
            @Value("${service.trusted-services}") List<String> trustedServices) {
        this.serviceJwtService = new JwtService(secret, Duration.ofMinutes(5));
        this.trustedServices = trustedServices;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) {
        String serviceToken = request.getHeader("X-Service-Token");

        // 如果是内网服务调用，必须验证服务 JWT
        if (serviceToken != null && !serviceToken.isBlank()) {
            try {
                JwtClaims claims = serviceJwtService.parseAndValidate(serviceToken);

                // 验证是可信服务
                if (!trustedServices.contains(claims.roles().iterator().next())) {
                    response.sendError(HttpStatus.FORBIDDEN.value(), "不可信的服务");
                    return;
                }

                // 设置服务上下文
                request.setAttribute("SERVICE_AUTHENTICATED", true);

            } catch (Exception e) {
                response.sendError(HttpStatus.UNAUTHORIZED.value(), "服务认证失败");
                return;
            }
        }

        filterChain.doFilter(request, response);
    }
}
```

#### 配置文件

```yaml

  jwt:
    secret: ${SERVICE_JWT_SECRET:change-this-in-prod}  # 必须使用环境变量

    - gateway-admin
```

```java
@Component
public class ApiKeyRequestInterceptor implements RequestInterceptor {
    @Value("${service.api-key}")
    private String apiKey;

    @Override
    public void apply(RequestTemplate template) {
        template.header("X-API-Key", apiKey);
    }
}

// user-service 验证 API Key
@Component
public class ApiKeyValidationFilter extends OncePerRequestFilter {
    @Value("${service.api-key}")
    private String expectedApiKey;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) {
        String apiKey = request.getHeader("X-API-Key");

        if (apiKey != null && !apiKey.equals(expectedApiKey)) {
            response.sendError(HttpStatus.FORBIDDEN.value(), "无效的 API Key");
            return;
        }

        filterChain.doFilter(request, response);
    }
}
```

## 5. JWT 密钥管理

### 5.1 密钥配置规范

```yaml
# ✅ 正确：使用环境变量
security:
  jwt:
    secret: ${JWT_SECRET:}  # 必须从环境变量读取
    ttl-seconds: 86400
    refresh-ttl-seconds: 604800

# ❌ 错误：硬编码密钥
security:
  jwt:
    secret: "my-super-secret-key-12345"  # 禁止！
```

### 5.2 密钥生成脚本

```bash
#!/bin/bash
# generate-jwt-secret.sh - 生成安全的 JWT 密钥

# 生成 256 位随机密钥（32 字节 Base64 编码）
SECRET=$(openssl rand -base64 32)

echo "JWT_SECRET=$SECRET" >> .env
echo "✅ JWT 密钥已生成并保存到 .env 文件"
echo ""
echo "⚠️  请将 .env 文件内容配置到生产环境："
echo "   - Kubernetes Secret"
echo "   - Docker 环境变量"
echo "   - 云厂商参数存储（AWS Parameter Store 等）"
```

## 6. 安全检查清单

### 6.1 部署前检查

```
□ 网络隔离
  □ Gateway 是唯一公网入口
  □ 内网服务不暴露公网端口
  □ 防火墙/Nginx 配置正确
  □ Kubernetes NetworkPolicy 已应用

□ 认证授权
  □ Gateway 正确验证 JWT 签名
  □ JWT 密钥未硬编码
  □ 密钥从环境变量/Secret 读取
  □ 服务间调用有认证（API Key 或 服务 JWT）

□ 数据安全
  □ 数据库密码不硬编码
  □ 使用加密连接（TLS）
  □ 敏感日志已脱敏

□ 监控告警
  □ 登录失败次数监控
  □ 越权访问告警
  □ 异常流量检测
```
